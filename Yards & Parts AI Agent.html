The agent core is the one piece every channel shares — it's what actually understands a customer, decodes their vehicle, and carries the conversation from "does this fit my car" to a closed order. Everything else is a tool the core calls: decode this VIN, check this fitment, look up this SKU, send this text, log this event. That's what makes "integrate with all ecommerce stores" realistic — the core never talks to Shopify's API directly, it talks to a CommerceConnector interface that Shopify implements today and WooCommerce/BigCommerce/etc. can implement later.

How to read this document Each numbered component below has a status chip, what it does, what's actually verified working versus what depends on a choice only you can make (mainly: which paid parts-interchange vendor, and which voice-AI vendor). 01 Ready — free, verified live

VIN decoding: year, make, model, sub-model

NHTSA's vPIC API decodes a full VIN into vehicle attributes. It's the U.S. government's own vehicle database, free, requires no API key, and has no rate limit for reasonable use.

Endpoint
GET https://vpic.nhtsa.dot.gov/api/vehicles/DecodeVinValuesExtended/{vin}?format=json
Auth
None
Returns
Make, Model, Model Year, Trim, Body Class, Engine Cylinders, Displacement (L), Fuel Type, Drive Type, Plant, and ~100 more fields per VIN
Cost
$0
Verified during this research A live query against a sample VIN pattern returned a correctly decoded 2011 BMW X3 xDrive35i — 3.0L inline-6, AWD, 300 hp, built in Munich — confirming the endpoint is live and the field set is rich enough to drive fitment matching (year, make, model, engine size and cylinder count are the fields that matter for engine/transmission interchange).

The one limitation to design around: "Trim" (sub-model) isn't populated for every VIN — older or lower-volume vehicles sometimes come back with year/make/model/engine but a blank trim. The agent should treat vPIC as the first pass and always read the decoded year/make/model/engine back to the customer for confirmation before quoting ("So that's a 2011 BMW X3 xDrive35i with the 3.0L six — sound right?") rather than silently trusting an incomplete decode.

Fallback path: if a customer doesn't have their VIN handy (common on the phone), the agent asks year → make → model → engine size conversationally instead — the same fields, just gathered by question instead of decode.

02 Needs a vendor decision

ACES/PIES & parts interchange

This is the part of your request I want to be direct about, because it changes how you plan the budget.

Key finding ACES (Aftermarket Catalog Exchange Standard) and PIES (Product Information Exchange Standard) are data formats maintained by the Auto Care Association — not a free database of "which part fits which car." The Association's own API, released in January 2025, gives you the reference tables (vehicle configurations, qualifiers, product categories, brand IDs) that the format is built from — the shared dictionary every supplier's catalog is supposed to speak. It does not contain actual fitment applications for engines, transmissions, or any other part. Every company that offers real interchange lookup (including Car-Parts.com, referenced in your own PDF) built that mapping themselves, part by part, and licenses access to it.

In plain terms: there's no free, complete "does this part fit this car" answer for the whole U.S. market. There's a free shared vocabulary (which is genuinely useful — see below), and there are paid vendors who did the actual mapping work.

What to use the free tables for

Auto Care's VCdb (Vehicle Configuration Database) is the standard vehicle taxonomy the whole industry keys against — base vehicle, sub-model, engine configuration, each with a stable ID. Mapping your own yard inventory to VCdb vehicle IDs (instead of free-text "2010-2013 Honda Civic") is worth doing on its own: it's what lets a future interchange vendor, or Shopify's own product data, line up with your inventory without manual re-entry later. This is a one-time data-modeling step your developer can do against the free reference tables.

What the prototype ships instead

Rather than block the whole build on a vendor contract, the prototype (section 4 of the code) defines an InterchangeProvider interface with a documented method signature, a mock implementation seeded with a few realistic sample interchange records so the sales flow is fully testable end-to-end today, and a stub file ready for whichever vendor you sign with — swapping providers means writing one class, not touching the agent.

03 Ready — Shopify is unusually well-suited to this

Shopify & the commerce layer

Shopify shipped exactly the primitive an AI shopping agent needs in 2026: a Storefront MCP server, built for this use case specifically.

Endpoint
https://{your-shop}.myshopify.com/api/mcp
Auth
None for standard read/cart tools
Tools exposed
search_catalog, get_product, get_cart, update_cart, search_shop_policies_and_faqs
Use for
Letting the agent search your live product catalog, build a cart, and answer policy/warranty questions during the conversation

For anything the Storefront MCP doesn't cover — precise inventory counts across locations, creating draft orders for a phone sale, applying a quote-specific discount — the agent uses the Admin GraphQL API (current version cycle: 2026-07) via a private custom-app access token scoped to just those permissions.

Multi-platform, without a rewrite

The agent core never calls Shopify directly. It calls a small interface:

class CommerceConnector:
    def search_products(self, query: str) -> list[Product]: ...
    def get_product(self, sku: str) -> Product | None: ...
    def check_inventory(self, sku: str) -> InventoryStatus: ...
    def create_cart_or_checkout(self, items: list[LineItem]) -> CheckoutLink: ...
    def create_order(self, items: list[LineItem], customer: Customer) -> Order: ...

ShopifyConnector implements it now, using Storefront MCP for reads and Admin API for writes. A WooCommerceConnector or BigCommerceConnector later is new code behind the same interface — nothing about the agent, the VIN decoding, or the fitment logic changes.

04 Ready — built on Claude's native tool-calling

Agent core & guided sales flow

One conversational core, driven by Claude with tool-calling, shared by every channel.

Bilingual by default, not by toggle

Claude detects the language a customer writes or speaks in and responds in kind — a customer who opens in Spanish gets the whole conversation in Spanish, including quotes, objection handling, and follow-up messages; a mixed-language customer gets handled fluidly. The one thing to store explicitly is the customer's confirmed preferred language on their lead record, so a human agent (or a follow-up SMS) picks up in the same language later.

Guided sales flow (the state machine)

1

Greet & qualify

Detect channel, language, and rough intent (fitment question / pricing / warranty / just browsing) within the first exchange — this is the "answer in 30 seconds, not 30 minutes" requirement from your pain-points doc.

2

Vehicle ID

Get VIN (decode via NHTSA) or year/make/model/engine by conversation. Confirm back to the customer.

3

Fitment & sourcing

Query the interchange engine, then check availability against your yard inventory and Shopify. Present exact match first, compatible alternatives if the exact part isn't in stock, with honest lead-time framing (ships today / 3 days / sourced in 7–10).

4

Quote & persona-aware pitch

Detect DIYer vs. mechanic vs. dealer from question style and adjust technical depth. Present price with the anchor-and-value framing your PDF already scripted ("industry standard $X, our price $Y with warranty").

5

Objection handling

Detects hesitation language and deploys your existing objection scripts (quality, fitment, installation, durability, trust, price), customized with the specific part's warranty and specs rather than generic copy.

6

Close or hand off

Completes checkout via the commerce connector, or — for a large/complex order, or if the customer asks for a human — books a callback and hands off with full context attached, never a cold transfer.

7

Follow-up

If the conversation stalls without a close, hands off to the follow-up automation layer (section 6) instead of just ending.

Every tool call in this flow — decode VIN, check fitment, check inventory, create order, log event — is logged with a timestamp, which is what makes the funnel-tracking and CRM reporting in section 7 possible without extra instrumentation work later.

Channels: chat, email, SMS, and phone

The agent core is channel-agnostic; each channel is a thin adapter that turns messages into the same conversation loop.

ReadyWeb chat

Embedded on your landing page and Shopify storefront. Lowest-effort channel to ship first — no telephony, no email deliverability to configure.

ReadyEmail

Outbound via SendGrid or Postmark (or Microsoft Graph API, since your team already works in Outlook — worth asking your developer which is less friction). Inbound replies parsed and routed back into the same conversation thread as a lead's chat/SMS history, so the agent has full context regardless of which channel the customer replies on.

Ready — reuses what you already pay forSMS

RingCentral's own SMS API (developers.ringcentral.com/sms-api) sends and receives texts from your existing business number — no new vendor needed for this channel specifically.

Needs a vendor decisionPhone / voice

Key finding RingCentral's own Voice API is built for call control and analytics (mute, hold, transfer, transcription via RingSense) — it has no speech recognition, text-to-speech, or real-time conversation hooks, so it cannot host an autonomous AI phone agent by itself. Building the "AI answers the phone and qualifies the lead" capability from your PDF requires a dedicated voice-AI platform layered on top.

06 Ready — automates a sequence you've already written

Follow-up automation & lead nurturing

Your PDF mentions a 7-email sequence already built — the agent's job here is timing and personalization, not writing new copy:

  • Drip delivery — the existing sequence sent automatically, timed to lead behavior rather than a fixed clock (e.g. slower cadence for a lead who's still browsing, faster for one who asked about price).
  • Smart re-engagement — if a customer goes quiet mid-conversation, the agent checks back with something specific ("that 2015 Camry engine you asked about is still available") rather than a generic nudge.
  • Appointment/callback scheduling — booked directly by the agent into whatever calendar your team uses, no human round-trip required.
  • Multi-touch nurturing — email, SMS, and chat reminders coordinated so a lead isn't hit with the same message on three channels at once.
07 Ready to hand your developer

CRM & reporting feed

09

Decisions only you can make

Everything else in this document can move forward today. These five can't.

  • Pick a parts-interchange vendor to license (start the Car-Parts.com conversation, since your team already scoped that integration) — blocks real nationwide fitment coverage.
  • Pick a voice-AI platform for phone calls (Retell AI recommended) — blocks the "AI answers the phone" capability.
  • Confirm with your developer whether the in-house CRM can accept an incoming event feed (webhook or API) — determines how section 7 gets wired up.
  • Issue a Shopify custom-app access token scoped for inventory/order writes — needed the moment the agent needs to do more than read your catalog.
  • Approve API usage budget for Claude (agent core) and whichever voice/SMS/email vendors are chosen — all are usage-priced, not flat licenses, so cost scales with lead volume.
